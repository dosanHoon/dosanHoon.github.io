## "하드코딩된 한글 다 찾아줘"

서비스에 영문 UI를 적용하면서 숙제가 하나 생겼다. 코드 곳곳에 남아 있는 하드코딩 한글 문구를 **전수로** 찾아서 `t()` 함수로 옮겨야 했다. 영어 로케일이 이미 라이브인 상황이라, 하드코딩 한글은 그대로 라이브 버그였다.

이런 반복 조사는 AI 에이전트에게 시키기 딱 좋은 일이다. 그래서 시켰다. 에이전트는 예상대로 grep을 돌렸다.

```bash
grep -rn '[가-힣]' src/
```

결과는 **1,364건**. 열어 보니 절반 이상이 이런 것들이었다.

- 주석: `// 검색 조건이 바뀌면 초기화`
- 이벤트 로깅 상수: `element_text: "업로드 버튼"`
- 테스트 픽스처와 스토리북의 mock 데이터
- 화면에 표시되지 않는 내부 상수

grep은 코드를 **텍스트**로 본다. 그래서 "화면에 노출되는 한글"과 "그냥 파일에 있는 한글"을 구분하지 못한다. 1,364건을 에이전트에게 하나씩 읽혀서 분류시키면 컨텍스트만 태우고, 사람이 훑자니 며칠짜리 노동이 된다. 둘 다 하고 싶지 않았다.

## 발상 전환: 린터를 일회용 검색 엔진으로

grep이 못 하는 그 구분을 이미 잘하는 도구가 프로젝트에 들어 있었다. ESLint다. 린터는 코드를 텍스트가 아니라 **AST(구문 트리)**로 본다. "JSX 텍스트 노드에 있는 한글"과 "주석에 있는 한글"은 AST에서 완전히 다른 노드다.

ESLint의 `no-restricted-syntax` 규칙은 [esquery](https://github.com/estools/esquery) 셀렉터로 임의의 AST 패턴을 잡을 수 있다. CSS 셀렉터로 DOM을 잡듯이, AST 노드를 잡는 것이다. 한글은 유니코드 범위(`AC00–D7A3`)로 매칭하면 된다.

```js
// eslint.config.mjs — 조사용 임시 규칙
"no-restricted-syntax": ["warn",
  // 화면 표시 텍스트 — 신호가 가장 깨끗하다
  { selector: "JSXText[value=/[\\uAC00-\\uD7A3]/]" },

  // {condition ? "저장" : "취소"} 같은 JSX 표현식 안의 리터럴
  { selector: "JSXExpressionContainer > Literal[value=/[\\uAC00-\\uD7A3]/]" },

  // 사용자에게 노출되는 속성만 골라서
  { selector: "JSXAttribute[name.name=/^(placeholder|title|label|alt)$/] Literal[value=/[\\uAC00-\\uD7A3]/]" },

  // 토스트 메시지
  { selector: "CallExpression[callee.object.name='toast'] Literal[value=/[\\uAC00-\\uD7A3]/]" },

  // 에러 메시지
  { selector: "NewExpression[callee.name='Error'] Literal[value=/[\\uAC00-\\uD7A3]/]" },

  // label/title/message 같은 UI성 키를 가진 객체 프로퍼티
  { selector: "Property[key.name=/^(label|title|placeholder|text|header|message)$/] > Literal[value=/[\\uAC00-\\uD7A3]/]" },
]
```

이 규칙을 설정에 **임시로** 꽂고 한 번 돌린다.

```bash
npx eslint src -f json > korean-audit.json
```

주석은 AST에 리터럴 노드로 존재하지 않으니 자동으로 빠진다. 로깅 상수는 위 셀렉터 어디에도 걸리지 않는다. 결과는 **179건**. 전부 실제로 화면에 노출되는 문자열이었다.

## 노이즈 제어가 승부처다

셀렉터를 어떻게 좁히느냐가 이 기법의 전부라고 해도 된다. 실측하면서 배운 것들:

**JSXText 하나만으로 시작하라.** 화면 표시 텍스트의 대부분(내 경우 179건 중 122건)이 여기서 나오고, 오탐이 거의 없다. 가장 깨끗한 신호다.

**넓은 `Literal[value=/한글/]`은 함정이다.** "리터럴에 한글 있으면 다 잡아"라고 하면 로깅 상수, 내부 enum, 데이터까지 쏟아져서 1,212건의 노이즈가 됐다. grep과 다를 게 없어진다. 반드시 속성명·호출 대상·프로퍼티 키로 맥락을 좁혀야 한다.

**정당한 한글은 제외 설정으로 걸러라.** 이벤트 로그 명세 파일, `__tests__`, `.stories.` 파일은 ignore에 넣었다. 특히 i18n 라이브러리의 한국어 기본 사전 파일은 "하드코딩"이 아니라 정상적인 폴백이므로, 해당 파일만 규칙을 끄는 override 블록을 따로 뒀다. 이걸 안 하면 결과 목록의 신뢰도가 무너지고, 목록을 받아 든 에이전트가 고치면 안 되는 걸 고친다.

## 밟았던 지뢰 두 개

**ESLint 9에서 `-f unix`가 사라졌다.** 예전 습관대로 쓰면 에러가 난다. 어차피 에이전트에게 넘길 거라면 `-f json`이 낫다. 뒤에서 다시 얘기한다.

**경로에 대괄호가 있으면 glob이 오인한다.** Next.js 프로젝트라 `src/app/[locale]/...` 같은 경로가 있는데, 이걸 파일 패턴으로 넘기면 glob이 `[locale]`을 문자 클래스로 해석해서 아무것도 매칭되지 않는다. 파일 패턴 대신 디렉토리 인자(`npx eslint src`)로 실행하면 피해 갈 수 있다.

## 결과: 숫자가 곧 작업 계획이 된다

두 개 워크스페이스를 조사한 최종 결과:

| 대상 | grep raw | AST 정밀화 | 내역 |
|---|---|---|---|
| 서비스 앱 | 1,364건 | **179건** | JSXText 122 · 속성 26 · 프로퍼티 24 · toast 4 · Error 3 |
| 공용 UI 패키지 | — | **166건** | 프로퍼티 83 · JSXText 64 · 속성 13 · Error 6 |

셀렉터별 분포가 곧 작업의 성격을 말해 준다. JSXText가 많으면 단순 치환이고, 객체 프로퍼티가 많으면(공용 패키지가 그랬다) 상수 정의를 옮기는 구조 변경이 섞인다. 파일별로 집계하면 어느 화면부터 칠지 우선순위도 바로 나온다. grep 1,364건에서는 절대 나올 수 없는 계획이다.

## 이게 왜 "AI 에이전트 꿀팁"인가

여기까지는 ESLint 팁이다. 진짜 하고 싶은 얘기는 이걸 **에이전트 워크플로우에 어떻게 넣느냐**다.

**1. JSON 출력은 에이전트가 그대로 소비하는 구조화 데이터다.** `-f json` 결과에는 파일·라인·컬럼·매칭된 셀렉터가 다 들어 있다. 에이전트는 이걸 파싱해서 파일별로 묶고, 우선순위를 매기고, 수정 작업을 배치로 쪼갠다. "grep 결과 1,364줄을 읽고 판단해"보다 토큰도 정확도도 압도적으로 낫다.

**2. 규칙은 꽂았다 뺀다.** 이 규칙은 조사용이지 상시 규칙이 아니다. 설정에 넣고 → 돌리고 → 결과만 챙기고 → 되돌린다. 커밋하지 않는다. 린터를 린터가 아니라 **AST 위에서 도는 일회용 쿼리 엔진**으로 쓰는 것이다. (물론 i18n 정리가 끝난 뒤 `error`로 승격해서 커밋하면, CI가 신규 하드코딩 유입을 막아 주는 상시 가드가 된다. 그건 별도의 결정이다.)

**3. 레시피를 에이전트 설정 파일에 박아 둔다.** 이 셀렉터 세트와 실행 방법을 CLAUDE.md나 커서 룰 같은 에이전트 지침 파일에 넣어 두면, 다음부터는 "하드코딩 한글 찾아줘" 한마디에 에이전트가 grep 대신 이 방법을 꺼내 쓴다. 에이전트에게 검색을 시키는 요령은 좋은 프롬프트가 아니라 **좋은 도구를 미리 쥐여 주는 것**이었다.

**4. 패턴은 한글 검색에 한정되지 않는다.** `new Error` 전수 조사, 특정 훅을 직접 호출하는 곳 찾기, 금지된 import 패턴 검출 — "코드에서 특정 구조를 전수로 찾아야 하는" 모든 작업에 같은 레시피가 통한다. esquery 셀렉터만 갈아 끼우면 된다.

## 정리

- grep은 코드를 텍스트로 보고, 린터는 구조로 본다. 전수 조사의 정확도 차이는 여기서 갈린다.
- `no-restricted-syntax` + esquery 셀렉터는 설정 몇 줄로 만드는 일회용 AST 검색 엔진이다.
- 승부처는 셀렉터의 정밀도와 정당한 예외의 제외 처리다. 넓게 잡으면 grep과 같아진다.
- AI 에이전트에게는 결과물(JSON)을 주지 말고 **방법(레시피)**을 줘라. 지침 파일에 박아 두면 그다음부터는 알아서 한다.

1,364건 앞에서 며칠짜리 노동을 각오했는데, 셀렉터 여섯 줄로 반나절 만에 끝났다. 도구를 만드는 데 쓴 30분이 가장 이득이 큰 투자였다.
