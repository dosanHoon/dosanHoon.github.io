## 에이전트를 한 번 쓰는 것과 굴리는 것

AI 코딩 에이전트를 쓰기 시작하면 보통 이 순서를 밟는다. 처음엔 채팅창에 붙여 넣고 물어본다. 다음엔 프로젝트에 지침 파일(`CLAUDE.md` 같은 것)을 둔다. 그다음엔 반복 절차를 슬래시 커맨드나 스킬로 만든다. 여기까지는 대체로 잘 된다.

그런데 다루는 레포가 넷이 되고, 매일 아침 확인해야 할 일감·PR·배포 상태가 생기면 다른 문제가 생긴다. **에이전트는 세션이 끝나면 전부 잊는다.** 어제 정한 브랜치 규칙, 지난주에 밟은 함정, 이 레포에서만 통하는 빌드 명령을 매번 다시 설명하게 된다. 그리고 잘 굴러가는 절차조차, 내가 채팅창을 열어야만 시작된다.

이 글은 그 지점에서 환경을 다시 짠 기록이다. 핵심은 프롬프트를 잘 쓰는 요령이 아니라, **에이전트가 도는 루프를 몇 겹으로 설계하고 그 루프의 어디에 사람을 남기느냐**다.

> 실제 사내 프로젝트에서 굴리고 있는 구성을 일반화해서 옮겼다. 레포 이름·계정·URL·업무 내용은 전부 가상의 예시로 바꿨고, 코드도 그대로 실행되는 스크립트가 아니라 구조를 보여주는 예시다. 가져갈 것은 구조와 개념이다.

## 0. 지형: 레포 4개와 허브 하나

일하는 대상이 이렇게 생겼다고 하자.

| 레포 | 성격 |
|---|---|
| `service-front` | 프론트 모노레포 (Turborepo + pnpm). 앱 5개, 공용 패키지 10개 |
| `service-api` | 백엔드 (Kotlin + Spring, 헥사고날 모듈 5개) |
| `mail-worker` | 외부 메일을 폴링·파싱하는 작은 서비스. API와 **코드 의존 없이 캐시 키 스키마로만 결합** |
| `service-docs` | 기획서·회의록 원본(SoT) 레포. 외부 도구에서 매일 자동 동기화 |

그리고 이 넷을 심볼릭 링크로 모아 둔 **워크스페이스 허브**를 하나 뒀다.

```bash
workspace/
├── service-front -> ~/dev/service-front
├── service-api   -> ~/dev/service-api
├── mail-worker   -> ~/dev/mail-worker
├── service-docs  -> ~/dev/service-docs
└── .claude/
    ├── CLAUDE.md          # 크로스 레포 규칙만
    └── agent-logs/        # 에이전트 실행 장부
```

허브를 둔 이유는 하나다. **"API를 바꾸면 프론트 스펙 파일도 같은 날 같이 머지해야 한다"** 같은 규칙은 어느 레포에도 속하지 않는다. 반대로 단일 레포 작업은 해당 레포로 `cd`해서 에이전트를 띄운다. 허브의 첫 줄에 그렇게 적어 뒀다. 이 구분이 뒤에 나올 메모리 함정의 원인이 된다.

## 1. 첫 번째 겹: 컨텍스트를 계층으로 쌓기

지침을 한 파일에 다 넣으면 두 가지가 동시에 망가진다. 토큰이 새고, 안 읽힌다. 그래서 4층으로 쪼갰다.

```
~/.claude/CLAUDE.md                 # 1. 전역: 사람에 대한 규칙
workspace/.claude/CLAUDE.md         # 2. 허브: 레포 간 규칙
service-front/CLAUDE.md             # 3. 레포: 구조·명령·경계
service-front/.cursor/rules/*.mdc   # 4. 상황별: 그 작업 때만
```

**1층(전역)에는 코드 얘기를 쓰지 않는다.** 나에 대한 규칙만 쓴다. 커밋 트레일러 규칙, 승인 없이 코드 수정 금지, 산출물 서명 규칙 같은 것들이다.

**3층(레포)은 짧게 유지한다.** 실제로 30~70줄이다. 구조 요약, 빌드/테스트 명령, 그리고 **경계**를 쓴다. 경계가 제일 값이 나간다.

```markdown
## 구조
- `apps/web-client` — 사용자 서비스 (주 작업 영역)
- `apps/legacy-portal` — 별도 서비스. 이 레포 작업에서 수정 금지
- `packages/ui` — 공용 컴포넌트. 변경 시 모든 사용처 검증 필수
- `packages/api` — 코드 생성 결과물(gitignored). 직접 수정 금지, 스펙에서 재생성

## 핵심 커맨드
- 빌드 게이트: `pnpm build:web-client`
  — 새 워크트리에서 맨 `tsc --noEmit`은 환경 타입 파일 부재로 가짜 에러가 쏟아진다. 신뢰하지 말 것
```

마지막 두 줄 같은 항목이 지침 파일의 존재 이유다. 이걸 안 써 두면 에이전트는 매번 `tsc --noEmit`을 돌리고, 가짜 에러 40개를 보고, 그걸 고치려고 한다.

**4층은 지연 로딩이다.** 지침이 계속 늘어나면 결국 전역 파일이 뚱뚱해진다. 그래서 "항상 읽을 것"과 "그 작업 때만 읽을 것"을 물리적으로 분리했다.

```markdown
## 개발 규칙 (항상)
@.cursor/rules/ui-components.mdc
@.cursor/rules/test-required.mdc

## 상황별 규칙 (해당 작업 때만 읽기)
- 영문 UI 카피 작업: `.cursor/rules/ui-text-en.mdc` 필독 — 카피 추측 금지, 스펙 우선
```

부수 효과로 얻은 게 있다. 룰 원본을 Cursor 쪽 디렉토리에 두고 지침 파일에서 임포트하면, **에이전트 도구를 바꿔도 룰이 살아남는다.** 도구는 갈아타게 되어 있다.

## 2. 두 번째 겹: 메모리 — 사실 하나에 파일 하나

지침 파일이 "규칙"이라면 메모리는 "겪은 일"이다. 규칙은 내가 쓰고, 메모리는 에이전트가 쓴다.

정착한 형식은 단순하다. **파일 1개 = 사실 1개.** 프론트매터에 종류를 박고, 인덱스 파일 한 줄로 색인한다.

```markdown
---
name: feedback-deploy-verify
description: 배포 브랜치 push 전에 반드시 자체 빌드 검증을 돌린다
metadata:
  type: feedback     # user | feedback | project | reference
---

배포 브랜치로 push할 때 pre-push 훅은 기본 브랜치를 기준으로 검사한다.
따라서 배포 브랜치의 머지 결과는 검증되지 않은 채로 통과한다.

**Why:** 이 구멍으로 빌드 깨진 커밋이 실제로 개발망에 올라갔다.
**How to apply:** push 전에 머지 결과 트리에서 직접 빌드를 돌린다. 관련 [[feedback-worktree]]
```

종류를 4개로 나눈 게 회수율을 갈랐다. `user`(내가 누구인지) · `feedback`(내가 준 교정, **반드시 이유 포함**) · `project`(진행 중 작업 상태) · `reference`(외부 자원 포인터). `feedback`에 이유를 안 쓰면 다음 세션에서 그 규칙이 응용되지 않는다. 규칙만 남고 판단 기준이 사라지기 때문이다.

`[[다른-메모리]]` 링크는 아낌없이 건다. 아직 없는 이름을 걸어도 된다. 그건 "나중에 쓸 것"의 표시가 된다.

### 밟은 함정: 메모리 네임스페이스는 cwd로 갈린다

에이전트 메모리는 보통 **작업 디렉토리 기준으로 네임스페이스가 갈린다.** 즉 허브에서 세션을 열면 프론트 레포의 메모리가 자동으로 로드되지 않는다. 이걸 모르고 허브에서 프론트 코드를 만졌다가, 레포 컨벤션을 어긴 커밋을 만든 적이 있다(디자인 토큰 대신 색상 값을 하드코딩했다).

해결은 심볼릭 링크였다.

```bash
# 레포를 가로지르는 규칙은 원본 한 곳에 두고, 허브 네임스페이스에 링크만 건다
ln -s ../../<front-namespace>/memory/feedback-deploy-verify.md .
```

현재 허브 네임스페이스의 메모리 80여 개 중 30여 개가 링크다. 한쪽에서 고치면 양쪽이 같이 바뀐다. 복사해 두면 반드시 갈라지고, 갈라진 규칙은 규칙이 아니다.

## 3. 세 번째 겹: 서브에이전트는 권한과 계약으로 정의한다

서브에이전트를 쓰는 이유를 "일을 나눠서 빨리"로 이해하면 절반만 맞다. 실제 이득의 큰 쪽은 **컨텍스트 오염 방지**다. 파일 40개를 훑는 조사를 메인 세션에서 하면, 그 40개가 세션이 끝날 때까지 컨텍스트에 남는다. 서브에이전트에게 시키면 남는 건 결론뿐이다.

그래서 에이전트 정의에서 신경 쓴 건 프롬프트보다 **도구 권한과 입출력 계약**이다.

```markdown
---
name: issue-analyzer
description: 버그 티켓 1건의 근본 원인·영향 파일·수정 가능 여부를 판정한다. 병렬 호출용.
tools: Read, Grep, Glob, Bash    # 쓰기 도구 없음 — 분석 전용
model: sonnet
---

# 계약
입력: { ticketKey, title, description, imagePaths[] }
출력(JSON): {
  root_cause: string,
  solvable: "yes" | "no",
  skip_reason?: string,
  affected_files: [{ path, line, why }],   # file:line 필수
  fix_strategy: string,
  test_hint: string
}

## 금지
- 코드 수정·커밋·push 금지 (도구도 없다)
- 근거 없는 단정 금지. 파일을 못 읽었으면 못 읽었다고 써라
```

여기서 실제로 효과가 컸던 세 가지.

**쓰기 도구를 아예 주지 않는다.** "수정하지 마"라고 프롬프트에 쓰는 것보다, `tools`에 `Edit`을 안 넣는 게 강하다. 실제 구성에서 쓰기 권한을 가진 에이전트는 딱 하나(그룹 단위 수정 담당)뿐이다.

**출력을 스키마로 고정한다.** 산문으로 받으면 메인 세션이 그걸 다시 해석해야 한다. `file:line`을 필수로 박아 두면 "아마 이 컴포넌트 근처"라는 답이 사라진다.

**모델을 티어로 나눈다.** 기계적인 조사는 저렴한 모델로, 판단이 필요한 리뷰는 중간 모델로, 어려운 검증만 상위 모델로. 나중에 나올 트리아지 등급과 붙여서 자동으로 갈리게 했다.

역할별로 10개쯤 만들었고, 계열은 셋이다. 디자인 시안 대조 계열(시안 스캐너 / 코드 DOM 매퍼 / 둘을 비교하는 differ), 티켓 처리 계열(분석기 / 수정기), 검증 계열(리뷰어 / 반증 검증기). **비교하는 에이전트에게는 결정 권한을 주지 않았다** — differ는 차이만 나열하고, 무엇을 고칠지는 사람과 메인 세션이 정한다.

## 4. 절차는 스킬로, 위험도로 쪼개서

스킬(또는 커스텀 커맨드)은 절차의 코드화다. 이건 많이 알려진 얘기라 짧게 하고, 실제로 사고를 막아 준 설계만 적는다.

**위험도별로 파일을 쪼갰다.** 배포 스킬을 환경별로 나누고, 되돌리기 어려운 환경은 스킬 자체에서 실행 권한을 뺐다.

| 스킬 | 하는 일 | 자율성 |
|---|---|---|
| `dev-deploy` | 개발망 배포 | 자동 머지·push까지 |
| `stage-deploy` | 스테이지 배포 | 자동 push, 사람에게 보고 |
| `prod-deploy` | 라이브 배포 | **PR 생성과 사전 점검까지만. 머지·push 절대 금지** |

"운영 배포는 조심해"를 프롬프트에 쓰는 대신, 조심할 절차를 아예 다른 파일로 만들고 그 파일에서 실행 단계를 지웠다. 클라이언트/어드민처럼 대상이 다른 것도 스킬을 나눴다. 하나로 합쳐 두면 인자를 헷갈릴 때 잘못된 환경에 배포된다.

## 5. 네 번째 겹: 루프 — 여기가 본론

여기까지는 "에이전트에게 좋은 재료를 쥐여 주는" 얘기였다. 재료가 갖춰지면 다음 질문이 온다. **누가 시작 버튼을 누르나.** 지금까지는 항상 나였다.

루프를 네 층으로 나눠서 봤다.

### L1. 세션 안 루프 — 검증과 재시도 상한

버그 티켓 여러 건을 처리하는 오케스트레이터 스킬을 이렇게 짰다.

```
1) 조회 → 처리할 티켓을 "진행" 상태로 표시 (재실행 시 중복 처리 방지)
2) 티켓 N건을 analyzer 서브에이전트로 한 번에 병렬 분석
3) 분류: 🟢자율 / 🟡사전검토(공유 컴포넌트·해석 갈림) / ⚪범위 밖
4) 그룹화: affected_files가 겹치는 티켓은 한 그룹 (union-find)
5) 그룹별 워크트리 생성 → 그룹 단위 병렬 수정 → 티켓별 커밋
6) 전 그룹을 상설 검증 워크트리에 통합 머지 → 유닛 + E2E + 브라우저 확인
7) 실패한 티켓만 재호출 (실패 로그 첨부). 티켓당 최대 3회
8) 3회 초과 → 그 티켓 커밋만 revert + 사람에게. 나머지 그룹은 계속 진행
```

설계에서 값이 나간 건 두 군데다.

**그룹화가 병렬의 전제다.** 그냥 티켓별 병렬로 돌리면 같은 파일을 여러 에이전트가 만져서 충돌한다. 영향 파일이 겹치면 한 그룹으로 묶고, 그룹 하나에 워크트리 하나를 준다. 그리고 **통합 머지에서 충돌이 나면 그룹화가 틀린 것**이므로 즉시 멈춘다. 이 신호가 꽤 유용하다.

**재시도에 상한과 롤백을 같이 둔다.** 상한 없는 재시도는 토큰을 태우고, 롤백 없는 포기는 애매한 커밋을 남긴다. 3회 실패는 "이건 사람이 봐야 하는 종류"라는 판정으로 취급한다.

그리고 자율 범위의 경계는 이렇게 정했다. **공유 컴포넌트의 동작·로직 변경은 확신이 있어도 사람 검토로 보낸다.** 옆 화면 회귀는 로컬 테스트가 가장 잘 놓치는 구멍이다. 단 문구·스타일 교체는 공통 적용이 정상이므로 자율로 둔다. 이 한 줄 예외를 안 두면 사소한 문구 수정마다 사람이 불린다.

### L2. 환경 검증 루프 — 로컬 통과는 통과가 아니다

배포를 자동화하면 곧 "배포됐다"의 정의 문제가 온다. push 성공은 배포 완료가 아니다. 그래서 스킬에 **실환경 폴링**을 넣었다.

```bash
# push 직전 현재 빌드 식별자를 저장해 두고, 바뀔 때까지 기다린다
BEFORE=$(fetch_build_id)
git push origin "$DEPLOY_BRANCH"

for i in $(seq 1 40); do          # 30초 × 40 = 최대 20분
  sleep 30
  NOW=$(fetch_build_id)
  [ "$NOW" != "$BEFORE" ] && { echo "deployed: $NOW"; exit 0; }
done
echo "timeout — CI 상태 확인 필요"; exit 1
```

포인트는 **폴링을 하나의 블로킹 루프로 돌린다**는 것이다. 에이전트가 "30초 기다렸다가 다시 확인할게요"를 반복하면 왕복마다 컨텍스트를 태우고, 중간에 다른 판단으로 새기도 한다. 한 번의 명령으로 조건이 만족되거나 타임아웃될 때까지 잡아 두는 편이 싸고 정확하다.

배포가 확인되면 **실환경에서 다시 검증한다.** 로컬 통과분이 실환경에서 깨지는 경우는 꾸준히 나온다. 한 번은 화면 이동이 10초씩 걸린 원인이 컨테이너 호스트 매핑 설정이어서, 코드에는 아무 문제가 없었다.

### L3. 스케줄 루프 — 헤드리스 워커와 잠긴 프롬프트

여기서 시작 버튼이 내 손을 떠난다. 에이전트 CLI를 **헤드리스(`-p`)로 스케줄러에 물렸다.** macOS면 launchd, 리눅스면 systemd timer나 cron이면 된다.

```xml
<!-- ~/Library/LaunchAgents/com.me.pr-monitor.plist -->
<key>ProgramArguments</key>
<array>
  <string>/bin/zsh</string>
  <string>/Users/me/.claude/pr-monitor.sh</string>
</array>
<key>StartInterval</key><integer>1800</integer>   <!-- 30분 -->
<key>StandardOutPath</key><string>/Users/me/agent-logs/pr-monitor.log</string>
```

래퍼 스크립트가 실제 설계다.

```bash
#!/bin/zsh
export PATH="$HOME/.local/bin:/opt/homebrew/bin:/usr/bin:/bin:$PATH"
cd "$REPO" || exit 1
git fetch origin main >/dev/null 2>&1 || true   # 워킹트리는 건드리지 않는다

PROMPT='내 담당 티켓 중 QA 통과분을 찾아 매칭되는 draft PR을 ready로 전환한다.
1) 티켓 목록 조회 2) 통과 상태인 티켓마다 제목에 티켓키가 포함된 열린 PR 검색
3) draft면 ready 전환 + 리뷰어 지정. 이미 ready면 스킵(멱등).
허용 동작은 [PR ready 전환], [리뷰어 지정] 둘뿐이다.
티켓 상태 변경·코드 수정·머지·다른 PR 조작·기본 브랜치가 아닌 PR 조작은 전부 금지.
마지막 줄에 "MONITOR: 전환N 스킵N 리오픈N" 한 줄 요약만 출력.'

claude -p "$PROMPT" --permission-mode bypassPermissions >> "$LOG" 2>&1
osascript -e "display notification \"$(tail -1 "$LOG")\" with title \"pr-monitor\""
```

무인 실행에서 지켜야 했던 것들.

**허용 동작을 화이트리스트로 못 박는다.** 무인 실행은 권한 승인 프롬프트를 우회해서 돈다. 그러면 "하지 말 것" 목록보다 "이 두 개만 해라"가 안전하다. 금지 목록은 언제나 새는 쪽이 있다.

**멱등성을 프롬프트에 요구한다.** 30분마다 도는 작업은 같은 대상을 계속 만난다. "이미 되어 있으면 스킵"이 없으면 알림이 30분마다 반복된다.

**출력은 마지막 한 줄 요약으로 규격화한다.** 로그 전체를 알림에 띄울 수 없다. `tail -1`이 그대로 알림 본문이 되게 하면 파싱이 필요 없다.

**LLM이 필요 없는 루프는 LLM을 빼라.** 처음엔 PR 자동 처리도 에이전트로 돌렸는데, 하는 일이 "목록 조회 → 조건 매칭 → API 호출"로 굳은 뒤에는 순수 파이썬 스크립트로 내렸다. 30분마다 도는 작업에서 토큰 비용이 0이 됐고, 동작은 더 안정됐다. **루프의 목표는 에이전트를 많이 돌리는 게 아니라 내 손을 떼는 것이다.**

현재 도는 잡은 여섯 개다. 상태 수집기(5분), 사이트 프로브(5분, UP→DOWN 알림), PR 자동 처리(30분), 문서 동기화 2종(하루 1회), 그리고 수집 결과를 보여주는 로컬 대시보드 서버. 아침에 브라우저 하나 열면 어제 밤 사이의 변화가 다 있다.

### L4. 학습 루프 — 실패가 곧 다음 룰이 된다

여기가 제일 재미있고, 제일 덜 알려진 부분이다. 자동화를 켜 두면 다음 질문이 온다. **이 에이전트가 잘하고 있는지 내가 어떻게 아는가.**

세 장치를 넣었다.

**① 장부(ledger) — 중복과 낭비를 막는다.**

```json
// agent-logs/review/ledger.json — 같은 커밋을 두 번 리뷰하지 않는다
[{ "repo": "front", "pr": 515, "head_sha": "a1b2c3d", "mode": "others", "reviewed_at": "..." }]
```

**② 실행 기록(runs.jsonl) — 회고의 입력이 된다.**

```json
{"ts":"","repo":"front","pr":0,"mode":"others|self|backtest","tier":"quick|standard|deep",
 "findings_total":0,"findings_by_sev":{"high":0,"med":0,"low":0},
 "user_action":"approved_all|partial|rejected","miss":[],"false_positive":[],"notes":""}
```

`miss`(사람은 찾았는데 에이전트가 놓친 것)와 `false_positive`(에이전트가 틀리게 지적한 것)는 나중에 채운다. 이 두 필드가 개선의 재료 전부다.

**③ 백테스트 — 정답지가 이미 있다.** 이미 머지된 PR 중 **사람 리뷰 코멘트가 달린 것**을 골라, 코멘트를 가린 채 에이전트에게 리뷰시키고 결과를 대조한다. 둘 다 발견 / 에이전트만 / 사람만(miss) / 오탐으로 채점한다. 별도 데이터셋을 만들 필요가 없다는 게 이 방법의 미덕이다.

**④ 반증 검증기 — 그럴듯한 오답을 걸러낸다.** 리뷰 에이전트의 지적을 다른 에이전트에게 넘기면서, 역할을 "확인"이 아니라 **"반증 시도"**로 준다.

```markdown
---
name: finding-verifier
tools: Bash, Read, Grep, Glob
model: sonnet
---
각 지적이 **틀렸음을 입증하려 시도**한다. 반증에 실패한 것만 CONFIRMED.
- 판정: CONFIRMED / REFUTED / INCONCLUSIVE + 근거 file:line + 재현 경로
- 지적별로 독립 판정한다. 앞 판정을 뒤 판정의 근거로 쓰지 마라
- 정적 분석만으로 도달 가능성을 CONFIRMED 하지 마라. 실환경 확인이 우선이다
```

"이거 맞아?"라고 물으면 에이전트는 잘 동의한다. "틀렸다는 걸 증명해 봐"라고 하면 다르게 움직인다. 실제로 오탐이 걸러졌고, 오탐을 조사하는 과정에서 **원래 지적과 무관한 실제 결함 두 건**이 나왔다.

여기서 비용 함정을 하나 밟았다. 지적마다 검증 에이전트를 하나씩 띄웠더니, 에이전트당 컨텍스트 구축 고정비(3~4만 토큰)가 N배로 붙어서 월 한도를 넘겼다. **PR당 검증 에이전트 하나에 지적 목록을 일괄로 넘기고, 프롬프트에서 독립 판정을 강제하는 쪽으로 바꿨다.** 병렬화의 이득과 고정비를 같이 계산해야 한다.

**그리고 마지막 연결.** 검증이 실패했거나 놓친 게 나오면, 그 교훈을 **해당 에이전트 정의 파일에 룰로 추가한다.** 예를 이렇게 얻었다.

- 스크린샷 자유 대조로는 정렬 같은 **구조 불변식 위반을 못 잡는다**(두 번 연속 실패, 두 번째는 "위반 없음"이라고 확신까지 했다) → 룰 추가: 정렬·간격은 브라우저에서 요소 좌표를 실측해서 단정(assert)으로 검증한다.
- 코드 주석의 자기 설명을 근거로 결함을 판정했다가 틀렸다 → 룰 추가: 주석은 근거가 아니다. 호출 체인을 끝까지 읽어라.

**이게 학습 루프의 실체다.** 모델을 학습시키는 게 아니라, 검증 실패를 지침 파일의 한 줄로 바꿔서 다음 실행에 주입한다. 파일로 남으니 세션이 끝나도 사라지지 않는다.

## 6. 사람은 어디에 남는가

자율성을 늘리는 작업은 결국 "사람 게이트를 어디에 몇 개 남기나"의 문제로 수렴한다. 지금 남긴 건 셋이다.

1. **외부에 노출되는 산출물** — PR 코멘트, 티켓 댓글처럼 남이 읽는 것. 초안까지는 자율, 게시는 승인.
2. **육안 검증** — 화면이 실제로 맞는지. 자동 검증이 가장 확실하게 놓치는 영역이다.
3. **지침 수정** — 에이전트가 자기 룰을 스스로 고치는 건 막았다.

그리고 승인 없이 팀에 나가는 산출물에는 **어느 에이전트가 썼는지 서명을 남긴다.**

```markdown
🤖 by agent (pr-reviewer)
<!-- agent=pr-reviewer reviewed=false -->
```

목적은 정직함 표시이기도 하지만 실용이 더 크다. 나중에 "이 리뷰 코멘트 이상하다"는 피드백이 오면, **그 피드백을 정확히 그 에이전트의 정의 파일에 꽂을 수 있다.** 내가 문구를 직접 고쳐 쓴 경우엔 서명을 뗀다. 그건 내 글이니까.

## 7. 밟은 함정들

값을 치르고 배운 것만 모았다.

**요약을 위임하면 원본이 사라진다.** 시안 정보를 서브에이전트에게 "요약해서 가져와" 시켰더니, 요약 과정에서 세부가 날아가서 잘못 구현됐다. 판단이 필요한 원본(디자인 컨텍스트, 스펙 원문)은 요약하지 말고 그대로 넘긴다.

**측정 환경이 조용히 다를 수 있다.** 자동화된 브라우저 탭이 백그라운드에 있으면 애니메이션 프레임이나 리사이즈 관측이 돌지 않는다. 이걸 모르고 레이아웃을 측정해서 **없는 버그를 두 번 만들고**, 그걸 고치려고 불필요한 코드까지 넣었다. 렌더링에 의존하는 측정은 전용 테스트 러너로 돌린다.

**"수정했다"는 보고를 믿지 마라.** 파일에 실제로 반영됐는지 확인하는 절차를 스킬에 넣었다. 치환 스크립트가 조용히 실패했는데 로그만 성공으로 출력한 사례가 있었다. 계측 로그가 안 찍히면 라이브러리를 의심하기 전에 내 수정이 파일에 있는지부터 확인한다.

**미재현 판정에 게이트를 걸어라.** "재현 안 됩니다"가 가장 위험한 결론이다. 접수된 증상을 다시 보는 것만으로 미재현을 선언하면, 접수자가 본 문제가 다른 이름으로 실재하는 경우를 놓친다. 실제로 "정렬이 어긋난다"는 티켓을 좌표 오차 0으로 미재현 처리했는데, 원인은 폰트 크기가 1px 달라 글리프가 영역을 꽉 채운 것이었다.

**토큰을 실측해서 등급을 나눠라.** 리뷰 깊이를 메타데이터만으로 먼저 분류한다(변경 규모, 고위험 경로 포함 여부, 신규 의존성 추가 여부). 얕은 건 저렴한 모델로, 깊은 건 파일 단위로 끝까지. 실측하니 얕은 리뷰와 깊은 리뷰의 비용이 2~3배 차이였다. 이걸 모르고 전부 깊게 돌리면 금방 한도에 닿는다.

## 정리

- 지침은 **계층**으로 쌓고, 상황별 룰은 지연 로딩한다. 한 파일에 다 넣으면 안 읽힌다.
- 메모리는 **사실 1개 = 파일 1개**, 종류를 나누고 이유를 함께 쓴다. 이유 없는 규칙은 응용되지 않는다.
- 서브에이전트는 프롬프트보다 **도구 권한과 출력 스키마**로 정의한다. 쓰기 도구를 안 주는 게 "하지 마"보다 강하다.
- 무인 루프는 **허용 동작 화이트리스트 + 멱등 + 한 줄 요약**. 그리고 LLM이 필요 없어진 루프는 스크립트로 내려라.
- 학습 루프의 실체는 모델 학습이 아니라 **검증 실패를 지침 파일의 한 줄로 바꾸는 것**이다. 실행 장부와 백테스트가 그 재료를 만든다.
- 자율성 설계는 결국 **사람 게이트를 몇 개 남기느냐**의 문제다. 나는 셋으로 줄였다: 외부 노출물 승인, 육안 검증, 지침 수정.

에이전트를 잘 쓰는 요령을 찾다가, 결국 **에이전트가 도는 환경을 짜는 일**을 하게 됐다. 프롬프트는 한 번 쓰면 사라지고 파일은 남는다. 남는 쪽에 시간을 쓰는 게 이득이 컸다.
