나만 쓰던 AI 자동화를 팀의 개발 환경으로 만들게 됨

처음에는 나만 잘 쓰면 된다고 생각함.

일감 조회, Figma 명세 추출, PR 리뷰를 Claude에게 시킴.

반복되는 절차는 스킬과 에이전트 파일로 남김.

내 컴퓨터에서는 꽤 잘 돌아감.

그런데 팀원에게 써 보라고 하려는 순간 문제가 생김.

파일을 어디에 복사해야 하는지, 어떤 MCP가 필요한지, 토큰은 어디에 넣는지 설명해야 했음.

업데이트할 때는 다시 복사해 달라고 해야 함.

이건 팀의 도구가 아니었음.

그냥 내 설정 파일이 많아진 것이었음.

프롬프트를 공유하는 것으로는 부족했음

팀에서 AI를 같이 쓴다고 하면 공용 프롬프트부터 떠올리기 쉬움.

실제로 필요했던 것은 그보다 넓었음.

공통 업무 맥락
→ 재사용할 작업 절차
→ 필요한 도구와 인증
→ 변경 권한
→ 결과 검증
→ 실패를 다음 버전에 반영

이 중 하나라도 개인 컴퓨터에만 있으면 같은 결과를 재현하기 어려움.

그래서 개인 설정에 있던 스킬과 에이전트를 사내 Git 저장소로 옮김.

Claude Code 플러그인 마켓플레이스 형태로 배포함.

팀원은 저장소를 내려받아 파일을 복사하지 않음.

마켓플레이스를 한 번 추가하고 필요한 플러그인만 설치함.

업데이트도 같은 경로로 받음.

업무 단위로 플러그인을 나눔

하나의 거대한 AI 도구로 만들지 않음.

실제 업무 경계에 맞춰 세 묶음으로 나눔.

플러그인 하는 일
업무 도구 일감·댓글·사내 문서·기획 명세 조회
Figma 도구 시안 추출, 코드 대조, 구현 전 계획
리뷰 도구 PR 분석, 발견 항목 반증 검증

Figma를 쓰지 않는 사람은 Figma 도구를 설치하지 않아도 됨.

PR 리뷰가 필요 없는 사람도 리뷰 도구를 빼면 됨.

외부 서비스 인증은 플러그인에 넣지 않음.

토큰과 OAuth는 각자의 사용자 환경에 둠.

플러그인은 무엇을 할지만 배포함.

인증 정보는 누가 실행하는지에 따라 분리함.

덕분에 공용 저장소에 개인 경로나 계정, 토큰이 들어갈 이유가 없어짐.

명령어를 외우게 하지 않음

팀 도구가 생겨도 사용법이 복잡하면 안 쓰게 됨.

그래서 별도 명령을 외우게 하지 않음.

평소 하던 말로 요청하면 맞는 스킬이나 에이전트가 선택되게 함.

"이 일감과 댓글 확인해줘"
"이 시안이랑 코드가 맞는지 봐줘"
"이 PR 리뷰해줘"

온보딩 문서에는 설치만 적지 않음.

필요한 인증, 설치 확인, 첫 동작 테스트, 자주 발생하는 오류까지 한 흐름으로 둠.

설명서를 읽고도 막히면 온보딩이 끝난 것이 아니기 때문임.

모든 맥락을 한 번에 넣지 않음

팀 AI라고 해서 모든 문서를 항상 읽게 하면 느리고 비쌈.

반대로 아무것도 주지 않으면 팀의 규칙을 모름.

그래서 컨텍스트를 세 층으로 나눔.

항상 읽는 것
  └─ 저장소 구조, 빌드 명령, 공통 개발 규칙

상황에 따라 읽는 것
  └─ Figma 구현, API 연동, 이벤트 로그, 영문 카피 규칙

여러 저장소를 건드릴 때 읽는 것
  └─ FE·BE·문서 간 동기화 순서와 배포 규칙

단일 저장소 작업은 그 저장소에서 시작함.

FE와 BE를 같이 바꾸는 작업만 별도 워크스페이스에서 시작함.

그 워크스페이스에는 코드보다 저장소 사이의 계약을 적음.

API가 바뀌면 어떤 스펙을 갱신하는지, FE와 BE PR을 어떤 순서로 묶는지 같은 내용임.

AI에게 모든 지식을 주는 대신 지금 하는 일에 필요한 지식의 입구를 줌.

조회와 변경의 권한을 분리함

AI가 일을 잘하는 것과 마음대로 쓰게 하는 것은 다른 문제였음.

읽기 전용 에이전트는 분석까지만 함.

PR 리뷰 에이전트는 코드를 읽고 발견 항목을 만들지만 GitHub에 댓글을 달지 않음.

Figma 대조 에이전트도 차이를 찾지만 무엇을 고칠지는 결정하지 않음.

일감 댓글처럼 외부 상태를 바꾸는 작업은 먼저 초안을 보여줌.

사용자가 승인한 뒤에만 등록함.

내 PR을 자동으로 고치는 흐름도 경계를 둠.

  • 타인 PR에는 push하지 않음
  • 내 PR 수정 뒤에는 기존 승인을 무효로 봄
  • 테스트가 통과해도 사람의 approve가 필요함
  • force push와 self approve는 금지함

자동화 범위보다 어디서 멈추는지를 먼저 정함.

AI의 리뷰도 다시 검증함

처음에는 리뷰 에이전트 하나가 찾은 문제를 그대로 믿었음.

오탐이 쌓임.

그래서 리뷰와 검증을 분리함.

PR diff
  → 리뷰 에이전트가 결함 후보를 찾음
  → 검증 에이전트가 틀렸다는 증거부터 찾음
  → 반증에 실패한 항목만 남김
  → 별도 게시 규칙으로 다음 동작을 결정함

검증 에이전트에는 “맞는지 확인하라”가 아니라 “틀렸음을 입증하라”고 시킴.

판정도 세 가지로 고정함.

  • 확인됨
  • 반증됨
  • 실행해 봐야 알 수 있음

확신이 없는 항목을 그럴듯하게 단정하지 못하게 함.

코드 위치와 재현 경로가 없는 지적은 버림.

AI를 한 번 더 호출한 것이 핵심은 아님.

서로 다른 역할과 판정 기준으로 한 모델의 확신을 견제하는 구조를 만든 것이 핵심이었음.

실제 실패가 공용 규칙이 됨

가장 많이 바뀐 것은 프롬프트가 아니라 실패 처리였음.

로컬 브랜치가 원격보다 오래되어 이미 바뀐 코드를 문제라고 판단할 뻔한 적이 있었음.

그 뒤 검증 에이전트는 판정 전에 최신 원격 코드를 확인하게 됨.

숨겨진 브라우저 탭에서는 애니메이션과 레이아웃 관찰이 제대로 동작하지 않았음.

그 뒤 렌더링 검증은 Playwright로만 하게 됨.

스크린샷의 요소 간격을 요소 너비로 잘못 해석해 Figma가 모순됐다고 보고한 적도 있었음.

그 뒤 수치 지적은 Figma 원본의 실제 필드를 다시 확인해야만 외부에 보고할 수 있게 됨.

구현 계획에서 토스트 문구가 빠졌는데 테스트는 모두 통과한 적도 있었음.

테스트에 그 문구를 확인하는 코드가 애초에 없었기 때문임.

그 뒤 구현 계획에 UI 문구와 테스트 여부를 함께 적는 커버리지 표가 들어감.

실패
→ 원인 확인
→ 에이전트 또는 스킬 규칙 수정
→ 버전 증가
→ 팀 업데이트

개인 자동화에서는 내가 다음에 기억하면 끝남.

팀 자동화에서는 기억이 아니라 배포 가능한 변경으로 남아야 함.

이 부분은 앞서 정리한 AI 에이전트 피드백 루프를 실제 팀 배포 구조로 옮긴 과정에 가까움.

팀원이 첫 PR을 보냄

팀 도구가 되었는지는 설치 횟수보다 다른 사람이 고칠 수 있는지로 판단할 수 있었음.

첫 팀원 PR은 화려한 에이전트를 추가한 작업이 아니었음.

Windows에서 동작하지 않는 온보딩 명령을 고침.

이미 등록된 MCP의 이름이 다를 때 생기는 오류도 문서에 추가함.

플러그인이 제공한다고 잘못 적어 둔 전제도 바로잡음.

그 변경이 중요했음.

내 컴퓨터에서 맞는 설명이 팀 전체에서 맞는 설명으로 바뀌었기 때문임.

이후 변경 규칙도 저장소에 둠.

  • 스킬이나 에이전트가 바뀌면 버전을 올림
  • manifest를 바꾸면 push 전에 JSON을 검증함
  • 개인 경로와 비밀값을 넣지 않음
  • 공용 도구와 저장소 전용 규칙을 섞지 않음

AI에게 지킬 규칙을 적는 저장소 자체도 팀의 코드가 됨.

아직 생산성 숫자는 없음

“개발 속도가 몇 배 빨라졌다”는 숫자는 적지 않기로 함.

아직 같은 조건으로 비교하지 않았고, 도입 초기이기 때문임.

대신 확인할 수 있는 변화는 있었음.

  • 팀원이 같은 설치 경로로 같은 도구를 받음
  • 업무 규칙이 개인 프롬프트가 아니라 Git 변경 이력으로 남음
  • Figma 구현, 기획 검토, PR 리뷰에 공통 출력 형식이 생김
  • 오탐과 누락이 다음 버전의 검증 규칙으로 들어감
  • 다른 OS에서 생긴 문제가 팀원의 PR로 수정됨

정량화하려면 앞으로 더 봐야 함.

온보딩 완료 시간, PR 리뷰의 유효 지적 비율, 같은 유형의 재작업 횟수 정도는 측정할 수 있을 것 같음.

지금 말할 수 있는 성과는 AI가 코드를 더 많이 만든 것이 아님.

팀이 AI에게 일을 맡기는 방식이 검토 가능한 형태로 남기 시작한 것임.

팀 레벨 AI 활용은 배포 문제였음

개인이 AI를 잘 쓰는 데에는 좋은 프롬프트가 중요함.

팀이 같이 쓰려면 다른 것이 더 필요했음.

설치할 수 있어야 함
업데이트할 수 있어야 함
같은 맥락을 읽어야 함
권한 경계가 보여야 함
결과를 검증해야 함
실패가 다음 버전에 남아야 함

결국 팀 레벨의 AI 활용은 프롬프트 작성법이 아니었음.

팀의 업무 방식을 코드처럼 버전 관리하고 배포하는 일이었음.

AI를 팀원처럼 만든 것이 아님.

팀이 일하는 절차를 AI도 따라갈 수 있는 형태로 만든 것에 가까움.
